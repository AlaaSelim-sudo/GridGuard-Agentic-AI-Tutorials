A complete agent workflow with three-phase LinDistFlow

Purpose: run one complete stage trace live, then compare voltage, restoration and evidence-integrity experiments from the supplied matched study. This is the modeling-specific lab inside the three-hour tutorial, not an additional three-hour session.

Follow the sequence: predict → run → inspect the actual response → challenge the result → acknowledge review.

The OpenDSS route represents the full feeder. The Python LinDistFlow route represents coupled MV phases and aggregates all secondary devices through ideal service transformers. The linear route requires NumPy and the supplied JSON network export; it does not import OpenDSS. Both use the same original trained DQN checkpoint. Full methods and references.

Three use cases, established methods, one workflow

The scientific problem determines the optimization model. The agent framework then organizes evidence, invokes that model, checks the result, and presents it for review. We use these established method families; we do not claim a universal ranking of industry adoption.

Use case General formulation Conventional comparator What the agent framework can contribute
Voltage support Three-phase Volt/VAR optimal power flow (OPF), repeated in a receding-horizon MPC The same OPF/MPC with fixed orchestration; local Volt/VAR droop is a distinct optional comparator Interpret the operating request, select an available solver, inspect infeasibility, and organize bounded recovery
Restoration Mixed-integer service restoration, maximizing priority-weighted load pickup subject to network constraints The same mixed-integer optimizer with fixed orchestration Translate approved priorities and equipment restrictions, assemble the plan, and explain rejected configurations
Cyber-attack response Weighted least-squares (WLS) state estimation, residual tests, and constrained redispatch from sufficiently trusted data The same estimator, detector, response policy and optimizer Gather evidence, route alarms, request an authorized recovery, and preserve an incident trace

2. Understand the numerical responsibilities

MPC solves a three-step finite-action problem. Its dimensionless utility is PV output divided by 8,000 kW, minus 0.15 times the fractional cap change, discounted by 0.95 per interval. An infeasible future makes the plan infeasible; it does not permit a myopic substitute.

The existing DQN proposes the action with the largest Q-value. The verifier requires both present model feasibility and a feasible horizon continuation. The best continuation beginning with that action may be at most 0.02 below the optimal MPC value. A rejected proposal may be replaced by the first MPC move; the attempt budget is two. Restoration instead enumerates available routes and an explicitly defined load-shedding catalog.

The table is the common contract. A stage can be PASS, REJECT, SKIPPED or PENDING. The response source distinguishes deterministic computations, actual Llama replies, and locally generated error fallbacks. The Execution stage proposes an action for simulation; it is not physical actuation.

6. Restoration and attack exercises

  1. Change CASE_ID to R2 and rerun the live cells. Inspect the restoration catalog, the short-route current ceiling, the disconnected noncritical load objects, and preserved critical demand. Then compare the other model's result.
  2. Change it to C1 (stale data) and C2 (biased aggregate voltage evidence). Explain why downstream stages are skipped. The readings are authored fixtures, not independent sensors or a WLS estimator.
  3. Use C3 and inspect the quoted malicious note in the planner journal. Identify the numerical checks the language response cannot disable.
  4. Inspect a case where the linear workflow proposes more PV than OpenDSS. Determine whether the final AC rejection is caused by LV scope, common-MV approximation, or both; do not infer the cause from the extrema alone.

Each live run gets a unique journal. The frozen request-intake experiments and original training checkpoint remain unchanged.
